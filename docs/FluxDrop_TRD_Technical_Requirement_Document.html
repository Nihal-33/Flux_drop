1. System Architecture Overview

FluxDrop implements a resilient Hybrid Edge-Cloud Architecture. High-volume file payloads are transmitted directly between client browsers via WebRTC SCTP DataChannels. When peers are not co-located or are behind restrictive symmetric NATs, payloads automatically route through Supabase Storage S3 buckets. The signaling and state sync layer is handled through a dual-mode communication pipeline: local Node.js Express/WebSocket daemon during local development, and direct Supabase GoTrue + PostgREST integration on cloud edge deployments (Vercel).

3. Supabase Relational Database Schema

The system utilizes a normalized relational schema within the public schema of PostgreSQL, mapped to Supabase Auth UUIDs.

3.1 Table: public.users

Column Type Description & Constraints
id UUID PRIMARY KEY Maps directly to auth.users.id from GoTrue.
username TEXT UNIQUE NOT NULL Public display handle (alphanumeric, 3-30 chars).
email TEXT UNIQUE NOT NULL Normalized lowercase email identifier.
password_hash TEXT NOT NULL Bcrypt hash for local auth or managed_by_supabase_auth.
storage_used BIGINT DEFAULT 0 Current consumed cloud buffer storage in bytes.
storage_limit BIGINT DEFAULT 10737418240 Maximum allocated cloud storage cap (10GB default).
security_question TEXT Selected challenge question for self-service PIN recovery.
security_answer_hash TEXT SHA-256 hash of normalized lowercase answer string.

3.2 Table: public.pins

Column Type Description & Constraints
id UUID PRIMARY KEY Default gen_random_uuid().
user_id UUID UNIQUE NOT NULL Foreign Key → public.users(id) ON DELETE CASCADE.
pin_hash TEXT NOT NULL SHA-256 or bcrypt hash of 4-6 digit workspace PIN.
failed_attempts INTEGER DEFAULT 0 Consecutive failed verification counter.
locked_until TIMESTAMPTZ Brute-force penalty timestamp (exponential backoff).

3.3 Tables: public.devices, public.files, public.udhar_*

Table Name Key Attributes Primary Purpose

4. Cryptographic Security & Recovery Protocol

4.1 Client-Side SHA-256 Hashing Implementation

To prevent sensitive cleartext passwords or recovery answers from ever hitting transit unencrypted, the frontend employs native Web Cryptography API primitives:

async function hashSha256(text: string): Promise<string> {
  const msgUint8 = new TextEncoder().encode(text.trim().toLowerCase());
  const hashBuffer = await crypto.subtle.digest('SHA-256', msgUint8);
  const hashArray = Array.from(new Uint8Array(hashBuffer));
  return hashArray.map((b) => b.toString(16).padStart(2, '0')).join('');
}

4.2 Dual-Mode API Routing Architecture

The client API layer in frontend/src/services/api.ts dynamically adjusts its communication protocol depending on host execution context:

Local Development Mode (localhost)

Routes requests to Express backend via /api proxy. If the proxy encounters a 404/502, it falls back to http://localhost:5000/api, with secondary fallback to direct Supabase client.

Cloud Deployment Mode (Vercel)

Automatically detected via window.location.hostname !== 'localhost'. Bypasses Express proxy to communicate directly with Supabase via secure TLS, preventing Mixed Content and 404 failures.
